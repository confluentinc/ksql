## Phase 1 — foundation

- Worked as written by copying common#1128 verbatim (MODULE.bazel, .bazelrc, presets, tools-bazel). `bazel mod deps`, `update_bazelrc`, `update_bazel_credential_helper` all clean on first try.
- Used the full `library_wrappers.bzl.tmpl` (common trimmed it); ksql needs the `java_library`/`maven_export` macros.
- Gap: the skill doesn't say what to do about `-parameters` / per-module `compilerArgs` overrides. Maven `<compilerArgs>` in a child **replaces** the parent's list, so the flag set differs per module; it matters for runtime behaviour (reflection on parameter names) and for class-byte parity.

## Phase 2 — dependencies & lockfile

- **What worked:** deriving `artifacts` mechanically from Maven itself — the union of `mvn dependency:list` (all scopes) across every reactor module, at Maven's resolved versions, with `version_conflict_policy = "pinned"`. Then diff the pinned lockfile against Maven's set and add every Coursier-only extra to `excluded_artifacts` (Maven's `<exclusions>` in the root dependencyManagement, the FIPS enforcer bans, broker-plugins' fabric8/srj/logback, ...). One repin later the lockfile == Maven's 538 coordinates + 12 Bazel-only tool coordinates (antlr4 tool chain, avro-compiler, JUnit platform). No ce/ccs oscillation: every kafka coordinate is pinned to the -ce build the resolved parent names, and none of the SR/common jars dragged -ccs in.
- 32 artifacts resolve to different versions in different reactor modules under Maven nearest-wins (e.g. `rocksdbjni` 10.10.1.1 vs 9.7.3 in rocksdb-config-setter, `jackson-datatype-jdk8` 2.22.1 vs 2.22.3, `reactive-streams` 1.0.3 vs 1.0.4). One resolver can't reproduce that; the majority version wins. Skill gap: say this explicitly — "one @maven per repo" is a behaviour change for multi-module reactors.
- The suggested `help:effective-pom` + read-it-by-hand approach does not scale to a 540-artifact closure with BOM-scoped properties (confluent-common-bom has its own `jackson.version`, different from the parent's); `dependency:list` per module is the only reliable source.
- Environment: CodeArtifact throughput here was ~150–700 kB/s with frequent `Premature EOF`; the cold Maven baseline took ~25 min mostly downloading, and both Coursier and Bazel's own http downloader needed retry loops (`--experimental_repository_downloader_retries`). Coursier and Bazel's repository cache are separate, so every jar is downloaded twice on a cold machine (three times counting ~/.m2).
- `fetch_sources = False` for convergence (as the skill suggests); see Phase 7 for the final state.
- Maven ranges pinned: parent `io.confluent:common [8.5.0-0,8.5.1-0)` → 8.5.0-831; `io.confluent.schema-registry.version` → 8.5.0-348. Kafka/common versions then follow from the parent's resolved properties.

## Phase 3 — BUILD authoring

- Scaffolded all 23 BUILD files from the poms with a throwaway generator (declared deps → labels, test-jar deps → `//<module>:<module>-tests`, provided → neverlink), then let strict-deps drive the rest. Automating the loop was the big win: parse every `buildozer 'add deps …'` hint **and** every `[strict] … TOOL_INFO: "<path>/header_<jar>"` line (some jvm_import header jars carry no label, so Bazel prints a path and no buildozer command — map the path back to `@maven//:group_artifact`), apply, rebuild. ~8 rounds to green; only 3 edges needed by hand. Skill gap: ship such a fixer script in `assets/` — on a 2,000-file reactor the manual loop is days.
- The fixer must rewrite `java_export` synthetic labels (`//m:m-lib`, `//m:m-project`) back to `//m`; strict-deps prints the internal names.
- The persistent-worker "error reading <file>.java" garbling did not occur here (Bazel 9.1.1 worker); the default strategy printed proper `[strict]` messages.
- Root-pom `<dependencies>` (log4j2 api/core/1.2-api, confluent-log4j2-extensions, logredactor, broker-plugins, provided spotbugs-annotations) are inherited by every Maven module and used directly from source → `KSQL_PARENT_DEPS` on every library. Skill gap: Phase 3 should call out root-pom `<dependencies>` (not just dependencyManagement) as implicit direct deps.
- **Annotation processors javac auto-discovers** from the Maven classpath were the main jar-content gap: log4j-core's `PluginProcessor` + `GraalVmProcessor` (→ `Log4j2Plugins.dat`, `META-INF/native-image/.../reflect-config.json`) in common/cli/test-util, and JMH's `BenchmarkProcessor` in benchmark. Nothing in the pom mentions them. Skill gap: tell the reader to diff the Maven jar's *non-class* entries against Bazel's early (it found these in one command).
- Codegen: antlr4 (`org.antlr.v4.Tool -visitor -listener -package <from dir> -Xexact-output-dir`) and avro (`SpecificCompiler` + `StringType.String`) as genrules → srcjar; Maven resource filtering (`${project.version}` in `version.properties`, copied from two resource roots) as a sed genrule over `$(maven_version)`. Jar entry sets then matched Maven exactly for every module (excluding `git.properties` / `META-INF/maven/**`).
- `-parameters`: applied per module exactly where the Maven `compilerArgs` keep it (9 modules); see Phase 0.
- Error Prone as warnings (`-XepAllErrorsAsWarnings`) like common; many latent findings (e.g. `DoubleBraceInitialization`) are printed, none fixed.
- `git.properties` (git-commit-id-plugin, `git.commit.id` only) is not reproduced; nothing in the code reads it. Noted as a parity delta.

## Phase 4 — testing

- **Shared test lib instead of `java_junit_test_suite`.** The confluent_rules macro compiles each `*Test.java` as its own javac action. For ksql (≈1,100 test classes, test classes referencing each other, every module's test-jar consumed by other modules) that is both slow and broken. Added `jvm_junit_test_classes` (tools-bazel/library_wrappers.bzl): the module's `src/test` compiles once into `<module>-tests` (which is also the published `tests` classifier and what downstream modules depend on) and each test class is a `java_junit5_test` with only `test_class`. Skill gap: offer this shape for large reactors.
- Test-class selection must mirror surefire **and** failsafe: surefire includes `Test*/*Test/*Tests/*TestCase` minus `@Category(IntegrationTest)`; the common parent's failsafe re-includes exactly the IntegrationTest category; the ksql root pom adds a second failsafe execution with `**/RestQueryTranslationTest*.java` (names that match no default pattern — easy to miss) and `**/rest/integration/**`. Abstract classes / classes with no tests are excluded at generation time. So `bazel test //...` ≈ `mvn install` (surefire + failsafe), not `mvn test`.
- **Vacuous passes.** ksql's test-util `ClassFinder` only scans classpath *directories* (Maven's `target/classes`); under Bazel's all-jar classpath, ~21 `ImmutabilityTest`/`*ModelTest`/`SqlTypesTest` parameterized tests found zero classes and passed with 1 (empty) case. Caught only by comparing per-class test-case counts with Maven's surefire reports. Fix without source changes: `classes_dir` (exploded main jar) prepended via the java stub's `--main_advice_classpath`. Likewise the QTT/RQTT loaders list resource directories via `getResourceAsStream(dir)`, which only works for directory classpath entries → exploded `test-classes` dir for functional-tests. Skill gap: add "compare per-class test-case counts against surefire XML for at least one module" to Phase 4's checklist — `Executed N tests: N pass` hides this.
- **cwd-relative paths**, generalized: `module_cwd_files` puts a module's files at module-relative runfiles paths (`ctx.runfiles(symlinks=…)`) and `root_symlinks` covers `../<sibling-module>/…`. Cleaner than the skill's root-package genrule (no output-name collisions across modules, per-test scope). Also covers ApprovalTests, which locates `*.approved.txt` next to the test *source*.
- Fixed-port/`exclusive` was not needed: ksql's embedded Kafka uses ephemeral ports. Integration tests do need `size = large` under parallel load (failsafe allows 3600 s forks); QTT needs `enormous` + `shard_count` (JUnit platform sharding works with vintage Parameterized).
- Testcontainers (Keycloak OAuth test) → `requires-docker`, skipped by default. Two tests fail under Maven on darwin-arm64 too (`ExpTest` last-ulp `Math.exp`, `KsqlResourceTest` stack-overflow probe) → `fails-on-darwin-arm64`, filtered only under `test:macos`.
- Two rest-app integration tests fail deterministically under Bazel but pass under Maven (an extra `_confluent-command` topic from the embedded CE broker's license service is counted). Same jar set as Maven's test classpath; classpath **order** differs (Bazel's is not Maven's declaration order). Tagged `bazel-known-failure`; open.
- One `@maven` resolver also means test-jar deps are transitive in Bazel (`//engine:engine-tests` drags engine's test-only deps like wiremock into rest-app tests) where Maven's test scope is not transitive. Harmless here, but a classpath-parity caveat.

## Phase 5 — publish parity

- 22 `java_export` targets at `io.confluent.ksql:<artifact>:$(maven_version)` (+ `tests` classifier via `classifier_artifacts`, mirroring the test-jar every module publishes). Kept on Maven: `ksqldb-parent`, `ksqldb-console-scripts`, `ksqldb-etc`, `ksqldb-package` (packaging=pom), `ksqldb-udf-quickstart` (maven-archetype), `ksqldb-docker` (sourceless jar + image), `ksqldb-api-reactive-streams-tck` (sourceless jar; its TestNG tests stay on Maven too).
- **Bug in the shipped `pom.tpl` (also in common#1128):** its header comment spells `{groupId}/{artifactId}/{version}/{dependencies}`, and those get substituted too — every generated POM had the full dependency list injected inside the XML comment. Fixed here by rewording the comment; the skill asset should be fixed.
- **`java_export` silently drops a module's own resources** when any dependency jar has an entry with the same path (maven_project_jar `--exclude`s the transitive runtime jars). Lost here: `log4j2.yaml` (rest-app, test-util) and root `version.properties` (common). Fix: `allowed_duplicate_names`. Skill gap: the Phase-5 parity step should diff jar *entry sets* of the `-project.jar` (not the `-lib.jar`) against Maven first.
- POM parity needs Maven's **effective** POM: the deployed module POM inherits 8 deps from `ksqldb-parent`/`io.confluent:common`, while Bazel's POM has no `<parent>`. The harness now checks (a) no dropped compile/runtime deps and (b) every extra Bazel dep (a strict-deps edge) is already in Maven's resolved closure; provided-scope deps (non-transitive) are informational. 22/22 pass. Scope delta: Bazel emits every dep as `runtime` (known, as in common).
- **Class-byte parity cannot hold with the default toolchain**, and common#1128's plan ("pin the CI Maven baseline to JDK 17") would not fix it: Bazel compiles with the javac bundled in `java_tools` (run on remotejdk_25), not the `--java_runtime_version` JDK. Measured: strict normalized sha FAIL 22/22 vs Maven/JDK 17; `--structural` (javap -c -p, lambda indices normalized) PASS 7/22 vs JDK 17 and **20/22 vs Maven built with JDK 25 javac**; the last 2 differ only in newer-javac codegen (enum `$SwitchMap` synthetic classes, inner-class ctor field-init order). A JDK 17 `VanillaJavaBuilder` toolchain is not possible either: VanillaJavaBuilder in this java_tools is class-file 65 (needs JDK 21+). Skill gap: state this up front and make the structural compare the default parity criterion, or align the Maven baseline javac with java_tools'.
- JDK 23+ javac disables implicit annotation processing; a Maven baseline built on JDK 25 needs `-Dmaven.compiler.proc=full` or the log4j plugin metadata disappears.

## Phase 6 — formatting

- Copied common's buildifier-only `format_multirun`; `bazel run //:format.check` clean after one `bazel run //:format`. google-java-format deferred (ksql never used it; ~3,100 files would churn).
- Checkstyle (`checkstyle/suppressions.xml`) and spotbugs (`findbugs/findbugs-exclude.xml`) gates stay in the Maven build — Handoff item.

## Phase 7 — wrap-up

- `fetch_sources` flipped back to `True` after convergence (478/539 artifacts have a sources jar); repin + fetch were quick once Coursier's cache was warm.
- Draft PR text kept outside the repo (public repo; Airlock push handled separately). No push, no PR, no publish from the session.
- **Maven baseline that works locally** (no system JDK on this laptop; reuse Bazel's hermetic JDK 17; default `~/.m2/settings.xml` is enough because CodeArtifact `maven/maven` serves the 8.5.x snapshots):
  - `export JAVA_HOME=$(bazel info output_base)/external/rules_java++toolchains+remotejdk17_macos_aarch64`
  - build: `mvn -B clean install -DskipTests -Dio.confluent.schema-registry.version=8.5.0-348 -Dcheckstyle.skip -Dspotbugs.skip -Ddocker.skip=true -Dmaven.gitcommitid.nativegit=true` (cold ≈25 min, mostly CodeArtifact downloads; warm ≈16 min observed, not a careful timing)
  - tests: the same without `-DskipTests` (surefire + failsafe). Validated on `-pl ksqldb-udf,ksqldb-common verify` (104 + 940 tests, 40 s) and single classes elsewhere. On darwin-arm64 add `-Dmaven.test.failure.ignore=true`: `ExpTest`, `KsqlResourceTest`, RQTT batch 0 and the Docker-only `ClientOAuthTest` fail under Maven locally.
- Skill gap: the skill has no guidance for the "parent POM is itself a range" + "the published parent has the kafka ranges already resolved" situation; reading `common-parent-<nano>.pom` from CodeArtifact gave the concrete kafka versions directly (`ce.kafka.version`, `kafka.version`), which made Phase 2 trivial.

## Post-handoff timing pass

- Skill gap (Phase 4): mirror surefire `rerunFailingTestsCount` (root pom: 3,
  surefire lane only; failsafe has none) as `flaky = True` on non-integration
  targets. A cold full run hit one failsafe-lane flake
  (`ScalablePushBandwidthThrottleIntegrationTest`), which Maven doesn't rerun
  either.
- The TCK's 4 TestNG tests were dropped from the Bazel build and stay on Maven. ksql is a public repo, and Airlock's proprietary-code scan flags a verbatim copy of the skill's `assets/BazelTestNgRunner.java`, because that asset lives in a private repo. Skill gap: any skill asset copied into a public repo needs a public home, or an Airlock release, first.
- Root-caused the two "Bazel-only" rest-app failures (`ClusterTerminationTest`, `TransientQueryResourceCleanerIntTest`). `kafka-test-common-runtime` (`DummyLicenseManagerService`) and `confluent-licensing-new` (the real `LicenseManagerServiceImpl`, which creates `_confluent-command`) both register a ServiceLoader `LicenseManagerService`, and the first on the classpath wins. Maven's classpath puts the dummy first in 17 of 21 modules (not engine/execution/rest-model/streams); Bazel put the real one first everywhere, because the inherited `broker-plugins` came early. Fixed with a `classpath_first` stub-first option on those 17 modules' tests. Skill gap (Phase 4): when the same jar set behaves differently, diff `META-INF/services` providers that appear in more than one jar and compare each module's provider order against `mvn dependency:build-classpath`.
- Maven parity for the remaining exclusions. `ClientOAuthTest` (Testcontainers) now runs by default like under Maven; opt out without Docker via `--test_tag_filters=-requires-docker`. The reactive-streams TCK's TestNG tests are back via the open-source JUnit Platform `org.junit.support:testng-engine`, with no custom launcher. Skill gap (Phase 4): contrib_rules_jvm's JUnit 5 runner fails ABORTED results unless the throwable is opentest4j `TestAbortedException`, so TestNG `SkipException`s from testng-engine fail the target. A small `single_version_override` patch counts ABORTED as skipped, as the JUnit Platform and surefire do. Worth upstreaming to bazel-contrib/rules_jvm.
